# Architecture

The reasoning behind the structure, and the trade-offs taken.

---

## The problem

The existing LEAN portal is a set of hand-authored ASP.NET pages. Every content
change — a new circular, a revised subsidy figure, a fresh programme schedule —
requires a developer and a release. The Ministry needs to publish without one.

That single requirement drives most of what follows.

---

## Layering

```
LeanPortal.Api             Controllers, authentication, middleware, composition root
      │  depends on
LeanPortal.Infrastructure  EF Core, migrations, seed, file storage, tokens
      │  depends on
LeanPortal.Application     DTOs, request contracts, mapping, service interfaces
      │  depends on
LeanPortal.Domain          Entities, enums, identity — no external dependencies
```

Dependencies point inwards. `Domain` knows nothing about EF Core or ASP.NET,
which keeps the entities readable and the model testable.

`Application` holds the shapes that cross the wire. Mapping is written by hand
in `MappingExtensions` rather than generated by a convention-based mapper: it is
a little more typing, but the API shape then never drifts silently when a
property is renamed, and a reader can see exactly what a client receives.

## Making the site editable

Three decisions do the work.

### 1. Pages are data, and so are their addresses

A `Page` carries a hierarchical slug — `about-scheme/financial-assistance`. That
slug is the URL, the breadcrumb trail and the sidebar grouping, all at once.

On the client, concrete Angular routes are declared first and a catch-all sits
last:

```ts
{ path: '**', loadComponent: () => …CmsPageComponent }
```

Anything the app does not recognise is resolved against the CMS by slug. An
editor publishing a page at a new address needs no front-end release. The cost
is that a mistyped URL takes an API round trip before it 404s, which is a fair
trade for a content site.

### 2. The landing page is composed, not coded

The home page has no fixed template. It is a `Page` with `Template = Blocks` and
an ordered list of `PageBlock` rows. Each block has a type, a heading, links,
and a JSON settings bag for the card-based bands.

The Angular home component is a dispatcher:

```
@for (block of page.blocks; track block.id) {
  @switch (block.type) { … }
}
```

Editors re-order, retitle, hide or remove any band from the block builder. The
band *components* are code — that is deliberate. A fully generic page builder
would let an editor produce a page that does not look like the rest of the
portal; a fixed catalogue of well-designed bands keeps the site coherent while
still removing the developer from routine change.

### 3. Everything else is configuration-driven

Nine resources — banners, FAQs, documents, statistics, login portals, scheme
levels and components, success stories, partners, programmes — share exactly the
same admin shape: a searchable table, a modal form, create/update/delete, and
re-ordering.

Rather than nine near-identical screens, each declares a `ResourceConfig`
(columns and fields) and one component renders it. Adding a resource is a config
entry and a route.

The same idea appears on the server: `AdminCrudControllerBase<TEntity, TDto,
TRequest>` carries the shared behaviour, including the permission split, and each
controller supplies only its query shaping, projection and field mapping.

## Request flow

**Public read**

```
Browser → Angular route → ContentService → HTTP
       → SiteController / PagesController / HomeController
       → EF Core (AsNoTracking, soft-delete filtered)
       → DTO projection → 5-minute output cache → Browser
```

The landing page is assembled server-side into one `HomeDto` — page, banners,
statistics, components, levels, portals, documents, posts, testimonials and
links — so the home route renders without a waterfall of requests.

**Admin write**

```
Console → AdminApiService → HTTP + Bearer token
       → [Authorize(Policy)] → Controller
       → HTML sanitisation → EF Core (audit columns stamped on save)
       → AuditLog entry → DTO → Console
```

## Key decisions

### SPA rather than server-rendered

A single-page app on IIS is a folder of static files plus a rewrite rule. Adding
Angular SSR would mean running Node on a Windows Server alongside IIS, which is
a materially heavier operational story for the Ministry's team.

The cost is initial SEO. It is mitigated: the API serves `/sitemap.xml` from the
published pages, every route sets its own title, description, canonical and Open
Graph tags, and content is server-rendered *as data* on the first request.
If crawler coverage proves insufficient, prerendering the ~30 published pages at
build time is the next step, and does not change the hosting model.

### Soft delete

Content entities carry `IsDeleted` and a global query filter. A deletion removes
content from the site but keeps the row, so the audit trail keeps its
references. Users are deactivated rather than deleted for the same reason.

### Blocking deletes instead of cascading them

Foreign keys default to `Restrict`, not `Cascade`, everywhere except genuine
parent-child pairs (a page and its blocks, an album and its images). Deleting a
page that still has children, or that a menu item points at, returns a 409 with
an explanation rather than quietly removing things the editor did not intend to.

### Server-side sanitisation

Rich text is sanitised on **write**, not on render. The database therefore never
holds unsafe markup, and the sanitisation rules cannot be bypassed by a second
client. The Angular `safeHtml` pipe only marks the already-clean HTML as trusted.

### Audit failures never fail the operation

`AuditService` catches and logs its own exceptions. An audit write failing must
not stop an editor from saving; the alternative — losing the content change —
is worse.

### sessionStorage for tokens

Admin tokens live in `sessionStorage`, so closing the tab ends the session.
That is the behaviour expected of a government administrative console, and it
narrows the window for token theft compared with `localStorage`. The trade-off
is that operators sign in more often.

## Things deliberately left out

**A rich-text WYSIWYG.** Content fields accept HTML through a monospaced editor.
A WYSIWYG is the obvious next addition, but it is a significant dependency
choice (licensing, accessibility of the editor itself, and the sanitisation
contract) that should be made with the Ministry rather than assumed. The
sanitisation layer is already in place to receive whatever is chosen.

**Drag-and-drop re-ordering.** Ordering is done with up/down controls, which are
keyboard-accessible by default and need no drag library. The reorder API accepts
a full ordered list, so swapping in a drag implementation later is a front-end
change only.

**The statistics sync job.** `Statistic.SourceQueryKey` exists and the field is
editable, but nothing populates it: the transactional LEAN schema was not
available. Counters are maintained by hand until that job is written.

**Automated tests.** The projects build clean and the flows are verified against
a live database and browser, but there is no test suite. For a system of this
size the first additions should be integration tests over the public content
endpoints and the admin authorisation rules.

## Where to change things

| Task | Location |
|---|---|
| Rebrand | `frontend/lean-portal/src/styles/_tokens.scss` — one file |
| Add a home page band | `BlockType` enum, a block component, a case in the home dispatcher, an entry in the block builder catalogue |
| Add a simple CMS resource | Entity + configuration + admin controller (extend the CRUD base) + a `ResourceConfig` + a route |
| Change what the API exposes | `Application/Contracts` and `Application/Mapping` — the DTOs are explicit |
| Adjust sanitisation | `Api/Infrastructure/ApiInfrastructure.cs`, `HtmlContentSanitizer` |
| Adjust rate limits | `appsettings.json`, `RateLimiting` |
